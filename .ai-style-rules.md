## Naming & State-Control Rules

- **Env var flags**: `SCREAMING_SNAKE_CASE`, prefixed by the owning script/skill (`GATEGUARD_DISABLED`, `DELIVERY_GATE_BLOCK`, `COMPACT_THRESHOLD`). Boolean flags read as the string `"1"` (never `true`/`false`), and always default to the non-blocking/safe behavior when unset.
- **JS variables/functions**: `camelCase`. Exceptions are wire-format fields mirrored verbatim from JSON payloads the script didn't design (`tool_name`, `tool_input`, `session_id`): keep those snake_case to match the payload, don't rename them on the way in.
- **Bash local variables/functions**: `snake_case` (`est_tokens`, `line_count`, `extract_field`). Top-level script constants (computed-once paths, thresholds, config arrays, e.g. `REPO_DIR`, `SCRIPT_DIR`, `CLAUDE_ONLY_SKILLS`) use `SCREAMING_SNAKE_CASE` like the env var flags above, even when not env-derived.
- **`require` ordering**: alphabetical, always Node core modules only; no external npm deps in any hook script. (No bash script here uses `source`, so there's no matching convention to state for it.)
- **Stdin handling**: every script that reads JSON from stdin uses the identical two-step pattern: a `readStdin()` helper that returns `''` on any read failure (its `catch {}` is intentionally bare, like most safe-default catches in these hooks; see DONTs), then `JSON.parse(readStdin() || '{}')` wrapped in its own try/catch that falls back to `{}` (or an immediate safe exit) rather than throwing.
- **Subagent tool-call detection**: a hook that must tell a main-thread tool call apart from one issued by a dispatched subagent checks the same four fields (`agent_id`, `agentId`, `parent_tool_use_id`, `parentToolUseId`; true if any is a non-empty string): `gateguard.js`'s `isSubagent()` and `hooks/claude/suggest-compact.js`'s inline check use the identical field list, copied per script rather than factored into a shared helper (see the duplicated-helpers DONT below). `agent_type` alone is deliberately excluded: it's also set for a whole session launched with `--agent`, which is main-thread, not delegated.
- **Multi-harness logic**: one script sniffs the input shape at runtime (`detectDialect`) and branches, rather than forking a copy per harness (Claude/Codex/Copilot). The three `hooks/<harness>/*.json` files exist only to *wire* the shared script into that harness's hook contract; they carry no logic of their own.
- **Multi-harness branching picks its mechanism by applicability** (refines the rule above): a hook whose payload shape actually differs across harnesses sniffs it at runtime (`detectDialect`, e.g. `gateguard.js`, which wires into Claude, Codex, and Copilot); a hook with no distinguishing input branches on a static flag baked into the JSON wiring at install time (`core-rules-digest.js`'s `--copilot` argv check, since a `UserPromptSubmit` digest print has no stdin payload to sniff); a hook installed only where the payload is already identical needs no branching at all (`delivery-gate.js`, Claude/Codex only, both sharing the same Stop payload contract). All three are house style; choose by whether the hook has a payload to inspect and whether that payload actually varies across the harnesses it's installed for. Don't "fix" the digest hook to use `detectDialect` (it has nothing to sniff), and don't add dialect-detection to `delivery-gate.js` (its installed harnesses already agree on the shape).
- **Subagent `model`/`effort` pinning**: `agents/*.md` pin `model` and `effort` in lockstep, but the lockstep pairing is per-agent-role, not a single fixed table keyed only on model name: `fable`↔`high` for the three read-only advisors (architect-reviewer, security-auditor, fable-advisor), `opus`↔`xhigh` for planner (the one role now using the tier the prior round called "valid but currently unused"), `sonnet`↔`high` for research/diagnosis/execution (researcher, debugger, executor), `haiku`↔`medium` for mechanical no-judgment edits (mechanic). `fable` no longer implies `xhigh` by itself; planner is the only `xhigh` pin left, reflecting a measured retiering (planner alone stayed pinned to the deepest-reasoning tier; the three advisors moved down a rung) rather than a uniform read-only-implies-strongest-effort rule. State the rationale inline in `description`, don't leave it implicit.
- **Skill frontmatter `description`**: optimize for routing first. Front-load the user's intent, concrete trigger terms, and the nearest negative boundary, never just a summary of what the skill does. Aim for a few sentences or a short paragraph, usually about 500 decoded characters when that preserves every routing signal; shorter and longer descriptions are both valid, and fresh positive or near-miss routing evidence justifies exceeding the target when extra clauses matter. Preserve failure-scar clauses that prevent known misroutes. The 1,024-character format maximum is separate; the 500-character review target is informational, never a CI or schema cap. [`skills/skill-activation/`](skills/skill-activation/SKILL.md) lints a related trigger-word heuristic and reports this soft length target.
- **Cross-skill references**: `[[skill-name]]` wiki-link syntax inside skill bodies (see `context-budget`, `skill-activation`) to point at a related skill without duplicating its content.
- **Copilot review-instruction files**: live at `.github/instructions/<bucket>.instructions.md`, one bucket per path scope (a repo-wide `applyTo: "**"` bucket for voice/hygiene/scope rules, plus one bucket per distinct area evidenced by the sources, e.g. `scripts`, `docs`). Frontmatter always sets `excludeAgent: "cloud-agent"`.
- **Hook denial pattern**: the default is loop-free by marking a gated path checked the moment the hook fires, regardless of whether that firing blocks or only warns; a file can only ever be gated once per session either way. `gateguard.js` is the reference instance and is now warn-by-default on Claude/Codex, deny-by-default on Copilot (see its Golden File entry above), so "loop-free by marking" no longer implies "marks at deny time" the way it did before this round. A hook gating on an external unlock event outside its own control (`plan-gate.js`, unlocked only by a `plan-and-track` Skill invocation elsewhere in the session) may deny repeatedly by design, and states that explicitly in its own header rather than leaving it to be inferred.
- **Vendored-skill attribution comment**: a skill adapted wholesale from an external repo (`frontend-design`, `webapp-testing`, both from `anthropics/skills`) carries the HTML comment described in the Golden File above immediately after frontmatter, plus a sibling `LICENSE.txt` with the upstream license text. `theme-factory` was a third instance of this category until this round retired it into `frontend-design`; see that Golden File entry for how a fold-in extends rather than drops the retired skill's attribution. A skill that's merely *inspired by* another repo's idea but rewritten (e.g. `humanizer`) instead gets a one-line "adapted from X" credit in `AGENTS.md`'s Skills section, no in-file comment or `LICENSE.txt`; the distinction is whether the file content is substantially the vendor's own text or a from-scratch rewrite. The same inspired-by/rewritten credit now also covers a standing rule, not just a skill: the action-first output rule folded into `rules/agent-guidelines.md`/`rules/core-rules.md` is credited with a one-line "adapted from X" sentence in `AGENTS.md`'s rule-mechanism section rather than a skill-anatomy in-file comment, since it was deliberately implemented as always-on behavior instead of the upstream's opt-in, explicitly-invoked skill form.
- **Reference material lives in `docs/`, not README or AGENTS.md**: exhaustive reference detail (the model-default table per harness, the full tiered-subagent roster with per-agent descriptions, per-hook behavior and wiring, installer idempotency rules) lives in `docs/*.md`, one topic per file, with the source file linking to it rather than inlining it. This is the "Be skimmable, not exhaustive" rule applied structurally, not just to prose density: when a README or `AGENTS.md` section grows into a reference table or a per-item enumeration, that's the signal to extract it to `docs/` (`docs/hooks.md`, `docs/installers.md` are AGENTS.md-sourced instances of the same extraction, alongside README's own `docs/models.md`/`docs/skills.md`).
- **Bash to PowerShell function mirroring**: `install.sh` and `install.ps1` mirror function-for-function (`copy_agents`/`Copy-Agents`, `frontmatter_field`/`Get-AgentFrontmatterField`, `toml_escape`/`ConvertTo-TomlEscaped`, `render_codex_agent`/`ConvertTo-CodexAgentToml`, `upsert_toml_default`/`Set-TomlDefault`, and now `copy_copilot_agents`/`Copy-CopilotAgents`, `render_copilot_agent`/`ConvertTo-CopilotAgentMd`, `copilot_tools`/`ConvertTo-CopilotTools`). The PowerShell name always uses an approved Verb-Noun cmdlet verb; when the bash verb already maps onto one (`copy` → `Copy-`), the mirror looks like a case-transform, but that's incidental, not the rule. An unapproved bash verb gets substituted for the nearest real cmdlet verb (`upsert_toml_default` becomes `Set-TomlDefault`, not `Upsert-TomlDefault`; `render_copilot_agent` becomes `ConvertTo-CopilotAgentMd`, same substitution already recorded for the Codex renderer); don't flag a mirror just because its casing differs from the bash name. `frontmatter_field`/`Get-AgentFrontmatterField` grew matching escape-decoding logic: single-quoted `''` is a plain global replace (`gsub`/`-replace`), safe because a doubled single-quote has no adjacency ambiguity to mis-handle, while double-quoted `\"`/`\\` decodes in one left-to-right pass rather than sequential global replaces, which would mis-handle a backslash immediately before a quote; both abort the install on an escape neither installer's decoder can render, rather than installing a silently corrupted rendered value into two harnesses; `install.ps1` factors its decode loop into a sibling `ConvertTo-DecodedDoubleQuoted` while `install.sh`'s lives inline in an awk function, and that's not a naming gap to close, since PowerShell and awk don't share a convention for when to extract a helper. The two do diverge on purpose in one spot, self-documented in both files' comments: `install.ps1`'s `ConvertTo-CopilotAgentMd` safely nests `Get-AgentFrontmatterField` inside the `ConvertTo-CopilotTools` call because PowerShell's `throw` is a terminating error that unwinds through the nesting either way, but `install.sh`'s `render_copilot_agent` must assign `frontmatter_field`'s result to its own local variable first, since bash's `set -e` only observes the outer command's exit status and would silently swallow an inner command substitution's abort. Don't reconcile these two shapes; the divergence is the correct mirror, not drift.

## DONTs

- **Don't factor the duplicated JS helpers (`readStdin`, `intEnv`) into a shared module.** Each hook script is copied standalone into a different harness's scripts directory at install time (`~/.claude/scripts/`, `~/.codex/scripts/`, `~/.copilot/scripts/`) with no shared `node_modules` or relative-import root; every script must stay self-contained and runnable in isolation. This is stated explicitly in each file's header comment; the duplication is intentional, not oversight. The same rule now also covers the mutation gate's quote-aware `splitShellSegments`/`detectOutwardMutations` classifier, duplicated byte-for-byte between `hooks/claude/plan-gate.js` and `hooks/codex/plan-gate-pilot.js` for the identical reason. The rule extends past hook scripts too: the bounded-live-run process-control helpers (`liveCaseTimeout`, `terminateChildTree`, `handleParentSignal`, the timeout/grace/force-kill staging in `runChildCase`, all gated by a `LIVE_CASE_TIMEOUT_MS` env var) are duplicated across [`skills/skill-activation/scripts/run-activation-cases.js`](skills/skill-activation/scripts/run-activation-cases.js), its sibling [`run-behavioral-smokes.js`](skills/skill-activation/scripts/run-behavioral-smokes.js), and [`skills/skill-comply/scripts/run-codex-cases.js`](skills/skill-comply/scripts/run-codex-cases.js), since a skill's own `scripts/` directory has no shared-module root across sibling skills either, same underlying reason as the hook-script case. The two `skill-activation` runners carry these helpers verbatim, but `run-codex-cases.js` is a parallel implementation of the same design rather than a byte-for-byte copy: it calls `fail()` where they call `die()`, `childProcess.spawn()` where they call a destructured `spawn()`, and caps captured output with its own `MAX_CAPTURE_BYTES` that the activation runners don't define. Don't flag those script-specific differences as drift to reconcile.
- **Don't let an error escape a hook script uncaught.** Every hook is wrapped in an outermost `try { main() } catch (err) { ...allow...; process.exit(0) }`. A hook that throws can fail a harness closed (Copilot) or otherwise wedge a session; always fail open, and always `process.exit(0)` explicitly rather than relying on the implicit exit code.
- **Don't add a `catch {}` with zero recovery action.** Every catch either assigns/returns a self-evidently safe default (`''`, `null`, `{}`, `[]`; needs no comment, e.g. `readStdin()`'s `catch { return ''; }`) or, when the fallback's safety isn't obvious from the code alone (it changes control flow, retries, or picks a non-trivial value), carries a one-line `/* comment explaining why */` or a `process.stderr.write('[Tag] ...')` diagnostic. An empty catch that does neither, silently discarding the error with no recovery at all, is not the house style.
- **Don't add a top-level `scripts/` directory.** Skill-owned scripts live at `skills/<name>/scripts/`, next to the `SKILL.md` that documents them; hook scripts live at `hooks/` (shared across harnesses) or `hooks/<harness>/` (that harness's own implementation, e.g. `hooks/claude/suggest-compact.js`, plus the JSON files that wire a shared script into that harness's hook contract). A hook that needs its own fixture-driven regression tests mirrors the skill convention one level down rather than inventing a new layout: `hooks/<harness>/scripts/run-<name>-*.js` (e.g. `hooks/codex/scripts/run-plan-gate-pilot-fixtures.js`) plus `hooks/<harness>/fixtures/<name>/cases.json`, next to the hook script it exercises. Nothing lives in a centralized, ungrouped scripts folder.
- **Don't hand-edit an installed copy.** `rules/agent-guidelines.md` and `rules/core-rules.md` are the only source of truth for rule text; every per-harness copy (`~/.claude/CLAUDE.md` managed block, `~/.claude/core-rules.md`, etc.) is generated by `install.sh` and is expected to be overwritten on the next install. Edit the repo copy and re-run `./install.sh all`.
- **Don't normalize the Copilot JSON hook shape to match Claude/Codex's**, or vice versa (see Golden Files above); the differing keys are a wire-contract requirement, not inconsistency to fix.
- **Don't skip the dependency gate in a new bash script.** When `jq` is required for the script to do its job (`install.sh`'s `need_jq()`), check `command -v jq` first and exit 1 with an `error: ...` message on stderr; don't let a missing dependency surface as a cryptic downstream failure instead. When one step is genuinely optional, like `install.sh`'s Copilot model default, warn and skip that step rather than exiting.
- **Don't silently regenerate or hand-edit a `.github/instructions/*.instructions.md` file without first checking for the `<!-- Generated by copilot-review-instructions; ... -->` marker comment.** Present → the file is skill-owned; safe to fully regenerate. Absent → don't assume hand-authored from that alone; ask the user to confirm actual provenance (the three original files turned out to be AI-generated in an earlier session, just predating the marker convention) before deciding whether to overwrite.
- **Don't treat the checked-in `hooks/<harness>/*.json` as the final hook artifact.** They are pre-substitution templates carrying a literal `__SCRIPTS__` placeholder; `install.sh`'s `render_hook` (and `install.ps1`'s mirror) bakes in the resolved absolute scripts dir (forward-slashed, even on Windows) at install time. Edit the placeholder form in the template, never a rendered absolute path; the rendered file lives in `~/.claude/settings.json` etc. and is overwritten each install (see the installed-copy DONT above).
- **Don't let `.ps1` be normalized to LF, or any `.sh`/`.js`/`.json`/`.md` to CRLF.** `.gitattributes` forces LF on shell/Node/JSON/markdown (a CRLF shebang breaks bash; hook scripts and JSON are read on every platform) and CRLF on `.ps1` only (the Windows-native installer). PowerShell is the one intentional CRLF exception; don't "normalize" it away.
- **Don't vendor a skill whose upstream license forbids redistribution.** The `docx`/`pdf`/`pptx`/`xlsx` skills carry a license that only permits use within Anthropic's own Services, so they're never copied under `skills/`; `install-office-skills.sh`/`.ps1` instead fetches them live from `anthropics/skills` at install time via a pinned third-party CLI. A skill under a permissive license (Apache-2.0: `frontend-design`, `webapp-testing`) can be vendored, but must carry the attribution comment and `LICENSE.txt` from the Naming rule above; check the upstream license before choosing vendor-in-repo vs. fetch-at-install for a new adapted skill.
- **Don't change the current Codex compatibility mapping or apply it to Copilot.** `render_codex_agent`/`ConvertTo-CodexAgentToml` renders `fable`/`opus` as `gpt-5.6-sol`, `sonnet` as `gpt-5.6-terra`, and `haiku` as `gpt-5.6-luna`, preserving `effort` as `model_reasoning_effort` and `tools` as `sandbox_mode` (Edit/Write present ⇒ `workspace-write`, else `read-only`). `render_copilot_agent`/`ConvertTo-CopilotAgentMd` still leaves `model` unset and drops `effort`, since Copilot's frontmatter has no matching fields; only its closed `tools` alias table translates. Because rendered copies vary in whether `model`/`effort` appear, an `agents/*.md` `description` should name the tier generically ("the roster's strongest-judgment tier", "a cheap execution tier") rather than a specific model name, so the prose stays accurate across all three harnesses; frontmatter remains the source of truth.
- **Don't interpolate attacker-controlled text straight into a GitHub Actions `run:` block.** [`.github/workflows/pr-body-lint.yml`](.github/workflows/pr-body-lint.yml) writes `${{ github.event.pull_request.body }}` to `$RUNNER_TEMP` through an `env:` var (`PR_BODY`) and a `printf '%s'`, never through direct expression interpolation inside `run:`, because a PR body is attacker-controlled on a fork PR and a `${{ }}` expression interpolated into a shell script is template substitution before the shell ever runs, not a shell-quoted value. The lint script itself then reads that file rather than an argument or env var holding the raw body. Apply the same env-var-then-file shape to any future workflow step that has to touch PR/issue title, body, or comment text.
- **Don't leave a colon-space inside an unquoted YAML frontmatter value.** A SKILL.md `description:` (or any frontmatter value) containing `: ` must be quoted: double quotes by default, single quotes when the text already contains a double quote, and when it contains both quote types, escape the chosen delimiter (`\"` inside double quotes, `''` inside single quotes) rather than switching representations; an unquoted colon-space reads as a nested YAML mapping key and invalidates the whole frontmatter block for a strict parser, even though this repo's own lenient line-regex parsers kept working, which is why the failure shipped silently across five skills before being caught. [`skills/skill-activation/scripts/run-activation-cases.js`](skills/skill-activation/scripts/run-activation-cases.js)'s `--precheck` `frontmatter_invalid_yaml` flag (and [`skills/rules-distill/scripts/scan-skills.js`](skills/rules-distill/scripts/scan-skills.js)'s matching quote-stripping) now lints for this and its mirror case, a quoted value containing an unescaped copy of its own delimiter. The same requirement covers `agents/*.md` `description:` fields too, not just SKILL.md: `architect-reviewer.md`, `fable-advisor.md`, `planner.md`, and `security-auditor.md` all quote their description now that it contains a `Read-only:`-style colon-space, while the unaffected agent files (`debugger.md`, `executor.md`, `mechanic.md`, `researcher.md`) stay unquoted; `run-activation-cases.js`'s new `--precheck-agents` mode lints this for agents the same way `--precheck` does for skills. `frontmatter_invalid_yaml`'s plain-scalar check has since widened past colon-space alone to the full YAML 1.2.2 plain-scalar grammar (cited by spec section/production number in the script's own comment): a leading indicator character, a leading `?`/`:`/`-` not followed by a non-space, a `:` followed by space/tab/end-of-value anywhere in the value, or a `#` preceded by space/tab anywhere in the value all now flag, not just the original `: ` case. A sibling `--precheck-agents`-only flag, `frontmatter_uninstallable_escape`, catches a narrower and different problem: a double-quoted value that is legal YAML (e.g. `\t`, `\n`, `\uXXXX`) but uses an escape neither installer's decoder knows how to render, since that decoder only implements `\"` and `\\`. A value can trip one flag, the other, both, or neither; don't collapse them into one check or assume `frontmatter_invalid_yaml === false` means an agent file is safe to install.
