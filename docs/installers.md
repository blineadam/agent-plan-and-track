# Installers reference

How `install.sh` and `install.ps1` deploy this repo into each harness, and the idempotency rules they hold to.

Two installers kept in lockstep: `install.sh` (bash + jq, macOS/Linux) and `install.ps1` (PowerShell 5.1, jq-free, Windows). Each has three targets (`install_claude` / `Install-Claude`, and so on) sharing common helpers (`copy_skills`, `install_digest`, `install_instructions`, `write_back`, `render_hook`). A parity note in both file headers lists the managed surface that must be mirrored; change one, change the other. Idempotent re-runs re-assert the repo's intended state without clobbering user content:

- Skills are repo-owned and copied with `cp -R` into the existing destination, which overwrites matching files but never removes user-added files sharing the dir. A reinstall also prunes repo-owned copies whose source left the repo, tracked per-dir by a `.plan-and-track-manifest`: a name that manifest recorded last time but the current install no longer produces is quarantined into a `.plan-and-track-pruned/` dot-attic (moved, not deleted, since a user could have installed their own content at a formerly repo-owned name that git can't restore). Only manifest-recorded names are ever touched, so a name the manifest never recorded (a user-added skill, an office skill) is never pruned, a missing manifest prunes nothing, and the prune is direct-children only (a renamed file inside a still-installed skill dir, or a stale hook script under the scripts dir, is out of scope). `NON_COPILOT_SKILLS` in install.sh lists the skills omitted from Copilot (currently `skill-comply`), so they install to Claude and Codex; everything else under `skills/` installs to all three harnesses. Subagents (`agents/*.md`) are repo-owned too: `install_claude` copies each file verbatim into `~/.claude/agents/` via `copy_agents`, `install_codex` renders each one into a native `~/.codex/agents/<name>.toml` (see below), and `install_copilot` renders each one into a native `~/.copilot/agents/<name>.agent.md` (see below).
- Codex subagents are rendered, not copied: each `agents/*.md`'s frontmatter and body map onto Codex's own TOML subagent format (`name`, `description`, `developer_instructions` required; `model`, `model_reasoning_effort`, `sandbox_mode` optional). The current compatibility mapping renders `fable`/`opus` as `gpt-5.6-sol`, `sonnet` as `gpt-5.6-terra`, and `haiku` as `gpt-5.6-luna`; `model_reasoning_effort` carries over 1:1 from `effort`, and `sandbox_mode` is `workspace-write` if `tools` includes Edit or Write, else `read-only`. The installers also re-assert bare `[features]` scalars `multi_agent = true` and `multi_agent_v2 = false`, preserving unrelated bare scalars and rejecting ambiguous quoted, dotted, or child-table forms before mutation.
- Copilot subagents are rendered too: each `agents/*.md`'s frontmatter and body map onto Copilot's own custom-agent Markdown format at `~/.copilot/agents/<name>.agent.md` (fenced YAML frontmatter with `name`, a double-quoted `description`, and `tools` as a YAML flow array; body unchanged below). `tools` maps through a closed alias table (`Read`->`read`, `Grep`/`Glob`->`search`, `Edit`/`Write`/`MultiEdit`->`edit`, `Bash`->`execute`, `WebFetch`/`WebSearch`->`web`), deduped in first-occurrence order, with an unknown source tool name warned to stderr and dropped rather than aborting. `model` is deliberately left unset, and `effort` is dropped entirely, since Copilot's agent frontmatter has no matching fields, so on Copilot the tier distinction shows up only as tool permissions.
- Instruction files get the repo content inside a marker-delimited managed block, from `<!-- agent-plan-and-track:begin (managed block: edit in the repo, not here) -->` to `<!-- agent-plan-and-track:end -->` (install.sh matches the begin marker by prefix); content a user adds outside the markers survives re-installs, and a file without markers is left alone entirely.
- Hook *scripts* are copied into each harness's scripts directory, with per-harness scopes: `core-rules-digest.js` and `gateguard.js` to all three, `delivery-gate.js` to Claude and Codex, and separate Claude/Codex `plan-gate.js` implementations. Codex uses an `apply_patch` disk-delta stamp because its installed skills do not produce Claude's Skill-tool invocation stamp; its scope and migration checks remain warn-only while its Bash mutation gate blocks. Hook *wiring* commands are templates carrying a `__SCRIPTS__` placeholder that both installers substitute with the resolved absolute scripts dir at install time (baked forward-slashed, so no `$HOME`/`%USERPROFILE%` expansion runs at hook time, which is what Claude Code's Windows hook-resolution bugs mishandle). The wiring is merged in only if not already present for Claude/Codex (`settings.json` / `hooks.json`; the digest idempotency check matches `core-rules`, covering both the new and any pre-existing inline command); a hook wired as more than one entry (Claude's `plan-gate.js` two PreToolUse entries, Codex's `plan-gate-pilot.js` apply_patch PreToolUse, Bash PreToolUse, and apply_patch PostToolUse entries) is checked and repaired per exact entry, so an install missing just one gets only that one appended, never a duplicate of the entries still present. Copilot's own hook files (`core-rules.json`, `pretooluse-gateguard.json`) are instead repo-owned and overwritten outright, with a `.bak` backup if one differed.
- Model defaults (Claude `opusplan` + `switchModelsOnFlag`, Copilot `auto`) are repo-owned and overwritten each install unless `PT_KEEP_MODEL=1`. Codex's plan-mode reasoning effort is separate and always overwritten regardless of `PT_KEEP_MODEL`, which covers model settings only.
- Claude's permission posture is opt-in and never changes on a bare install. `PT_BYPASS_PERMISSIONS=1` sets `permissions.defaultMode` to `bypassPermissions` and `skipDangerousModePermissionPrompt` to `true`; leaving the variable unset is the opt-out, so a pre-existing stricter `defaultMode` survives a re-install untouched. `PT_KEEP_MODEL` does not cover these two keys. Separately, `enabledPlugins["frontend-design@claude-plugins-official"]` is set to `false` unconditionally on every install: this repo ships its own `frontend-design` skill and the plugin bundles a second skill of the same name, which is a routing collision.
