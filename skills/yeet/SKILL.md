# Yeet

Publish local work with `git` + `gh` as a draft PR, see it through Copilot review while it is still a draft, and mark it ready for review only once the threads and the body are final.

## Before starting

Confirm GitHub CLI is installed and signed in with `gh --version` and `gh auth status`; if either fails, stop and ask the user to install `gh` or run `gh auth login`. Then note where the work stands: the branch (`git branch --show-current`), uncommitted changes (`git status -sb`), and the last few commits (`git log --oneline -5`).

## Naming

- Branch: short kebab-case description of the change when starting from the default branch.
- Commit message and PR title: a plain sentence describing the change; follow the target repo's own convention (e.g. Conventional Commits) where one exists.

## Publish

1. On the default branch, create a topic branch: `git checkout -b <description>`. Already on one: stay.
2. Stage and commit the task's files; don't sweep in unrelated changes with a blanket `git add -A`.
3. Check the commit message for AI self-attribution (a `Co-Authored-By:` trailer naming an AI tool, a "Generated with ..." footer, a `Claude-Session:` trailer) and amend it away if present.
4. Run the project's checks if not already run.
5. Push with tracking: `git push -u origin <branch>`. A non-fast-forward rejection means the remote branch moved under you, so pull to reconcile it and push again, taking any conflict git reports to [[resolving-merge-conflicts]] rather than force-pushing over the divergence. A rejection from authentication, branch protection, or a server-side hook is a different problem that pulling will not fix.
6. Write the PR body to a temp file with real newlines, then `gh pr create --draft --title "..." --body-file <file>`; never inline `--body` with `\n` escapes. The PR stays a draft through every step below until step 15 flips it, so reviewers who watch the ready-for-review queue see a finished body and closed draft-time threads, not work in progress. Editing an existing body later goes through `gh pr edit <n> --body-file <file>` under the same rules, and must never drop an image the body already carries: rewriting a body from scratch silently deletes one, so start from the current body and edit it. Absent the repo's own PR template: `## Summary` first, an optional `## Implementation`, then exactly one of `## Test plan` or `## Verification`. Describe the change as it stands, never the review history: no known-limits, review-round, or alternatives-considered heading, with residual risk going in the verification section. Run the prose through [[humanizer]]. The body gets the same self-attribution check as step 3, and a claude.ai session link counts. Read `references/pr-body.md` before writing or editing the body: it covers paragraph, list, subsection, and backtick shape for a skimming reader.

## Copilot review

7. Check whether the repo auto-requested a review with the GraphQL `reviewRequests` connection on the PR node: `gh api graphql -f query='query { repository(owner:"{owner}", name:"{repo}") { pullRequest(number:<n>) { reviewRequests(first:100) { nodes { requestedReviewer { __typename ... on Bot { login } ... on User { login } } } } } } }'`. `requestedReviewer` is a union, so the inline fragments are required to read a login at all; `... on Bot` names Copilot, and `... on User` keeps human reviewers visible in the same result. REST `GET repos/{owner}/{repo}/pulls/<n>/requested_reviewers` cannot serve this check: it omits bot reviewers, so an empty response there proves nothing about Copilot; it stays valid for confirming a human reviewer's request. On a draft, expect to make the request yourself rather than treat it as the fallback: a ruleset's `copilot_code_review` rule skips drafts unless its `review_draft_pull_requests` parameter is on (read the rule with `gh api repos/{owner}/{repo}/rulesets/<id>`), and an account-level automatic-review setting may request nothing on a draft, so the query above is the test, not the config. If Copilot is absent and no Copilot review exists yet, request one with `gh pr edit <n> --add-reviewer '@copilot'`, the only spelling that resolves. `gh api -X POST repos/{owner}/{repo}/pulls/<n>/requested_reviewers -f "reviewers[]=copilot-pull-request-reviewer[bot]"` is the REST equivalent where that alias is unavailable. Confirm the request stuck by re-running the `reviewRequests` query, never by parsing a POST response. A `@copilot review` comment is a silent no-op that still returns 201. Read `references/copilot-review-notes.md` when a GitHub call behaves differently than this step says.
8. Capture the head SHA, then check `gh api --paginate repos/{owner}/{repo}/pulls/<n>/reviews` for a review by `copilot-pull-request-reviewer[bot]` carrying a matching `commit_id`, and re-check that the head has not moved before trusting the match. Check once before waiting at all: where the repo auto-requests, the review has usually already landed by the time you first look. A review object can appear before the pass has finished writing its comments, so wait for a completion signal too: the reviewer drops out of the GraphQL `reviewRequests` connection (step 7's query) when it finishes, and where Actions runs are visible a successful `dynamic/agents/copilot-pull-request-reviewer` run at the same SHA says the same thing. Whenever you do wait, bound it and report a timeout rather than looping forever, since a disabled or failed run never lands, and wait with a mechanism that leaves the session answerable: a backgrounded command, or the harness's own wait or monitor facility. Never a foreground `sleep`, and never a shell loop around one. The reviewer is spelled differently per surface: `copilot-pull-request-reviewer` in GraphQL, `copilot-pull-request-reviewer[bot]` on REST `/reviews`, and `Copilot` on REST `/comments`; use each surface's own spelling rather than normalizing to one. Never accept a review count as the test: your own replies post as `COMMENTED` entries in this same list.
9. Fetch the findings themselves. `/reviews` carries only the review objects, so read `gh api --paginate repos/{owner}/{repo}/pulls/<n>/comments` too and select entries whose `pull_request_review_id` matches that review's `id`, joining on the id rather than an author login. `--paginate` is load-bearing on both calls: each endpoint returns 30 results per page by default (100 is the maximum page size, not the default), and a silently short page reads exactly like a clean review. Read the review body as well: lower-confidence findings are listed there instead of being posted as threads.
10. Triage every finding as a hypothesis, not a verdict: confirm it's real before fixing, prefer the root-cause fix over the minimal patch, and dispute with a stated reason when it's wrong or an already-accepted tradeoff.
11. Commit and push accepted fixes before answering anything, so the PR holds the new code by the time a thread is marked resolved. Then reply on each thread with what was done (the fix and its commit, or the dispute) via `gh api -X POST repos/{owner}/{repo}/pulls/<n>/comments/<comment-id>/replies -f body=...`.
12. Resolving needs a different id than replying. `resolveReviewThread` takes a GraphQL thread node id (`PRRT_...`), which no REST response carries, so query the `reviewThreads` connection for each thread's `id`, `isResolved`, and `comments(first: 1) { nodes { databaseId author { login } } }`. That root comment's `databaseId` is the REST comment id from step 9, so it is the join key back to your triage. This connection paginates too and caps at 100 nodes per page, so walk it with `pageInfo { hasNextPage endCursor }` and aggregate every page before filtering or counting: a thread past the first page is never replied to, never resolved, and never counted by step 14. Resolve only threads that are unresolved, whose root author is `copilot-pull-request-reviewer`, and whose root `databaseId` matches a finding you actually triaged and replied to: a thread that clears the first two tests but not the third belongs to a pass that landed mid-loop, so return to step 9 and triage it rather than resolving a finding nobody read. Leave threads opened by people alone: resolving one hides feedback nobody accepted and can wrongly satisfy a branch protection rule that requires resolution. An unresolved or reply-less Copilot thread is unfinished work.
13. Re-request a review only when a fix is itself high-risk or hard to verify directly; verify mechanical fixes by running them. Each re-requested pass repeats steps 8 through 12 in full against the new head, since a fresh pass can raise fresh findings.
14. Before calling the loop closed, and again immediately before anything irreversible like a merge, re-read the GraphQL `reviewRequests` connection (step 7's query), the unresolved-thread count, and every Copilot review id on the PR. All three matter: a pass whose findings sit only in the review body leaves no unresolved thread and no pending reviewer, so the first two signals read clean while an unread review exists. Scope the review-id query to the PR rather than the current head, since step 11 pushes each accepted fix and the head has moved past every review you triaged. Compare the ids against the ones you have already triaged and read any new one before acting. CI status is a fourth signal, and a merge needs it: every entry in `gh pr view <n> --json statusCheckRollup` must pass (a check run only when `COMPLETED` with `SUCCESS`, `NEUTRAL`, or `SKIPPED`; a status context only with `SUCCESS`), and an empty rollup is not a pass. A pending check means wait, bounded and backgrounded as step 8 describes. A failed check means read its log and name the cause before acting; a failure that looks unrelated to the change (a timeout, a flaky runner) is cleared only by a rerun of that job passing on the same SHA (`gh run rerun <run-id> --failed`), never by reasoning alone. Make the merge itself enforce this; each `&&` stops the chain before `gh pr merge` on a moved head, a pending or failed entry, or an empty rollup:

    ```bash
    info="$(gh pr view <n> --json headRefOid,statusCheckRollup)" &&
    [ "$(jq -r .headRefOid <<<"$info")" = "<sha>" ] &&
    jq -e '[.statusCheckRollup[] | if .__typename == "StatusContext" then .state elif .status != "COMPLETED" then "PENDING" else .conclusion end] | length > 0 and all(. == "SUCCESS" or . == "NEUTRAL" or . == "SKIPPED")' <<<"$info" >/dev/null &&
    gh pr merge <n> --squash --match-head-commit <sha>
    ```

    A check taken before a wait proves nothing about the state after it, so recheck at the moment you act, not once at the end of triage.

## Ready for review

15. Only after step 14 reads clean and the body is final, images included, mark the PR ready with `gh pr ready <n>`; the draft-to-open switch is what a reviewer sees, so nothing is edited after it except in answer to a review. Where automatic review skipped the draft, this switch starts a fresh pass at the current head, so repeat steps 8 through 12 and then step 14 against it. The flip can also start new checks, so step 14's CI gate applies to the head after it. The loop is closed when that pass is triaged too, not when the draft-time passes were.
