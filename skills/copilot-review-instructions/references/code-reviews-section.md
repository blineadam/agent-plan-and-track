# The `# Code reviews` section of `.github/copilot-instructions.md`

Read this before generating or refreshing that section (Step 6 of SKILL.md).

Copilot reads `.github/copilot-instructions.md` as repository-wide custom
instructions, applied to requests made in the context of the repository and
[enabled for Copilot code review by default](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).
Those docs describe the file's contents as natural-language Markdown and
document no inclusion directive. Instructions are combined by Copilot reading
each recognized file on its own, the path-scoped files from Step 3 among them,
rather than by one file importing another. A line like `@../AGENTS.md` is
therefore inert text, so this file should not try to pull the conventions in.
It tells the reviewer where they live and how to review, in a `# Code reviews`
section this skill owns.

The section is four prose paragraphs, in this order, following this skeleton
(placeholders in angle brackets), which is canonical:

```markdown
# Code reviews

<!-- Generated by copilot-review-instructions; edits here are overwritten on the next run. -->

Repository conventions live in <links to the sources Step 1 found>, and in the
path-scoped files under `.github/instructions/` (<bucket file stems>), which are
generated from <the sources backing them>. This file covers how to review, not
what the conventions are.

Do not comment on what CI already blocks: <each check that runs on a pull
request>. Everything else in the instruction files is enforced only by review,
so do comment on it.

Review correctness first, then readability, then maintainability. Say plainly
which findings block a merge and which are suggestions, and give the reason a
finding matters rather than asserting it.

The bar is "better", not "perfect". A PR that improves the codebase should not
be held up over style preferences no written convention supports.
```

Sourcing rules for the skeleton's placeholders:

1. **Convention links.** Relative links to the sources Step 1 actually found,
   and only those: the project's instructions file (`[AGENTS.md](../AGENTS.md)`,
   or `CLAUDE.md`), `.ai-style-rules.md` at the repo root, a `CONTRIBUTING.md`.
   Never link a file this project does not have, since Step 1 accepts a project
   whose conventions live only in its README. Name each bucket from Step 2 by its
   file stem and say which gathered sources back it, the same pointer Step 3
   puts inside each bucket.
2. **CI checks.** Name each check that actually runs on a pull request: the
   workflows with a `pull_request` trigger, plus any check GitHub runs from its
   default setup with no workflow file (CodeQL, for example), which a grep of
   the repo misses, so confirm the list against a recent PR's checks. Name only
   checks that really run in this project, not a generic set (Step 4's rule).

Apply the project's writing-voice rules to the prose (see Anti-patterns in
SKILL.md).
